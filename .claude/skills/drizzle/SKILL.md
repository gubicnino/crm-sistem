# Drizzle conventions (this project)

- Schema: single file, `db/schema.ts`. Client: `db/index.ts`. Migrations: `db/migrations/`, generated by `npm run db:generate` — **never hand-write migration SQL, never edit a migration that's already been applied.**
- Config: `drizzle.config.ts`, dialect `postgresql`.
- Timestamp helpers: `db/_helpers.ts` — `timestamptz(name)`, `createdAt()`, `updatedAt()` (has `$onUpdate`), and `timestamps` (spread both: `...timestamps`).
- All queries live in `db/queries/**` and go through the `db.select()`/`.insert()`/`.update()`/`.delete()` builder API — this codebase does not use Drizzle's relational `db.query.*` API anywhere; keep new code consistent with that.

## Every query function takes a `TrainerScope` first

This is the tenant-isolation mechanism CLAUDE.md describes — see `lib/tenant.ts`. In practice, in `db/queries/**`:

```ts
export async function getLead(scope: TrainerScope, leadId: string): Promise<Lead | null> {
  const [lead] = await db.select().from(leads).where(scoped(leads, scope, eq(leads.id, leadId))).limit(1);
  return lead ?? null;
}
```

`scoped(table, scope, ...extraConditions)` ANDs a `trainerId` predicate with whatever else you pass; `ownedBy(table, scope)` is the bare predicate alone. Never write `eq(table.trainerId, someString)` by hand outside these helpers.

A function that's genuinely cross-tenant (the cron reconciler scanning all trainers, the public unsubscribe page bootstrapping a scope from a leadId) is named with an explicit `Unscoped` suffix — e.g. `getLeadByIdUnscoped` — with a comment explaining why it has to be. Don't add a new unscoped function without that same justification and naming.

`eslint.config.mjs` enforces that `@/db` (the raw client) can only be imported from `db/queries/**` — that's what makes "every query is scoped" a structural property, not just a convention to remember.

## Primary keys & uniqueness

- Domain tables: `uuid("id").primaryKey().defaultRandom()`.
- Auth.js adapter tables (`users`, `accounts`, `sessions`, `verificationTokens`) are the one exception — their shape is dictated by the `@auth/drizzle-adapter` contract (composite PKs on `accounts`/`verificationTokens`, a `text` id with `$defaultFn(() => crypto.randomUUID())` on `users`). Don't use that shape as a template for a new domain table.
- Business uniqueness on domain tables goes in a `uniqueIndex`, never a composite PK — e.g. `leads_trainer_id_email_unique` on `(trainerId, email)`, `trainers_user_id_unique` on `userId` (this is what makes one-login-per-trainer a DB-level guarantee, not just app logic), `scheduled_emails_lead_id_sequence_step_attempt_unique` on `(leadId, sequenceStep, attempt)` (the index that makes double-scheduling structurally impossible — see the `email-sequences` skill).

## The `pgEnum` exception is narrow — don't extend it casually

Every evolving value set in this schema is `text().$type<SomeUnion>()`, with the union defined in `db/types.ts`. Exactly two columns break that pattern as a **deliberate, reviewed exception**: `pipelineStageEnum` and `leadSourceEnum`, because both are product vocabulary the whole app branches on (pipeline UI, analytics, sequence triggers), not operational plumbing expected to churn. CLAUDE.md gates changing either set behind "ask first." If you're tempted to add a third `pgEnum`, that's a strong signal to ask first too, not to treat the existing two as a green light.

## JSONB columns are always concretely typed

`jsonb("col").$type<SomeInterface>()`, never `Record<string, unknown>` — see `ApplicationQuestion`, `LeadAnswers`, `EmailDoc`, `CronRunStats` etc. in `db/types.ts`. `lib/validation/email-doc.ts` is the actual runtime security boundary for the `EmailDoc` shape (rich-text bodies); the `$type<>()` annotation alone is compile-time only.

## The upsert idiom: insert-with-onConflictDoNothing, then a follow-up update

Used for "is this a genuine insert" logic (see `createLeadFromIntake` in `db/queries/leads.ts`) instead of a single `onConflictDoUpdate` — it turns "was this new?" into a plain JS boolean (did the insert return a row) rather than a Postgres `xmax = 0` trick, and lets the follow-up `update()`'s `set` differ based on business rules (e.g. only an `application` resubmission may advance `stage`, and only out of `email_lead`):

```ts
const [inserted] = await db.insert(leads).values({...}).onConflictDoNothing({ target: [leads.trainerId, leads.email] }).returning();
if (inserted) return { lead: inserted, isNew: true };

const [updated] = await db.update(leads).set(/* conditional fields */).where(scoped(leads, scope, eq(leads.email, input.email))).returning();
return { lead: updated, isNew: false };
```

Reach for this pattern (rather than `onConflictDoUpdate`) whenever the update-on-conflict branch needs conditional logic beyond "overwrite with the new values."

## Dynamic imports inside query files

Some `db/queries/**` functions dynamically `await import(...)` a module partway through (e.g. `setLeadStage` importing `lib/email/cancel.ts`), instead of a top-level import. This isn't incidental — it's avoiding forcing every consumer of that query file (including a plain `listLeads` read, or a test exercising an unrelated function) to eagerly load a module with real side effects at import time, such as `lib/email/client.ts` throwing if `RESEND_API_KEY` is unset. Follow the same pattern when a new query needs to call into `lib/email/**`.
